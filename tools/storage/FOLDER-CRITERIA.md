# Physical writers and the offline folder destination

Old: report and avatar writers are deferred from inventory. No folder uploader, destination receipts, category restore or declared media omission exists.

New: actual avatar blob, original manifest and upload receipt writes and report uploads register unique physical paths with actual stored bytes, preserve unchanged categories and deduplication, and leave preview/format refusals before writes. Report inventory failure removes its newly created file. Both writers have behavioural proof before the deferred declaration is cleared. JSON sidecars are physical text files, separately optional under the text policy; image blobs remain pictures.

Why: measured category costs and a folder upload must cover the bytes the actual writers create, including sidecars, without counting references or original image sizes.

Writer proof: tests/storage-physical-writers.test.ts. Immediate neighbours: tests/storage-inventory.test.ts, tests/avatar-uploads-share-stored-pictures.test.ts, tests/unnamed-report-files.test.ts. Each new criterion receives red before implementation, control, a production mutation and restore.

Old: destinations save policy but have no transport; receipts and occupancy are unknown, restore has no selected-category contract.

New: an independent folder command opens only read-only source settings/SQLite, stages then atomically publishes a weekly base or one cumulative change against that base, and verifies complete file SHA256/size manifests and SQLite integrity on restore. Paths, links, concurrent file changes, mismatched inventory and corrupt packs are refused without publishing success. Reads use SQLite iterators and fixed file buffers, including full manifests stored on disk. Existing destination packs are retained and count toward this office's held bytes. Core is always retained beyond the limit; optional files and history fit the actual held budget, with exact omission rows. Every attempt journals bytes, omissions and errors locally; 80 percent retains a C notice and one secretary line for ordinary office ingestion. Settings reads bounded receipt metadata.

Core preserves all declared tables and schema, all non-session record content and office chat, people/agents and governance/seal/warrant evidence, and structured revision pins to closure. Optional run payloads keep identity stubs needed by core relations; unpinned history and API logs obey saved policy. Tables not explicitly optional or security-cleared remain core, including future schema parts. Copy scrubbing uses the canonical secret declarations and byte search, and never reads host credentials. Transcript paths come from registered session/visitor facts; role comes from agents' cards, never paths. Policy exclusions and absent legacy returned files are declared truthfully. A restore's media omission index distinguishes deliberate exclusions from unexplained missing files in file/image/audio/video report renderers.

Why: one usable offline backup needs a bounded and verifiable restore, independent core safety, truthful policy omissions and host-only durable receipts.

Proof: tests/storage-folder.test.ts (base/change/deletion/restore; schema/core/optional/pins/secrets; roles/policy; exact held limits/journals; failure/path/corruption). tests/storage-receipts.test.ts covers receipt read and idempotent ordinary-job ingestion. tests/storage-restore-media.test.ts covers declared media omissions and unexpected absence. Browser evidence extends the storage settings and report fixtures at all four widths in English and both themes. Immediate neighbours: tests/storage-destinations.test.ts, tests/storage-destinations-page.test.ts, tests/report-media.test.ts when present. No live fixture or live server is used.

Reference comparison: the host Python tool's complete docstring and implementation were read. Preserve Sunday or absent-base full upload, new/changed hashes compared to base, full daily target manifest, deleted-file removal at restore and every SHA256/size check. The new folder format uses directories and an indexed SQLite manifest rather than tar/zstd and an in-memory JSON map; it extends the store set and refuses unsafe/concurrently changed paths. The reference itself is not moved or changed.

Criterion refinement: OLD scenario headings claimed threshold/unindexed/secret/governance coverage without populated fixtures. NEW actual over-threshold and regular unindexed files, populated key/token hashes searched in restored bytes, nested target/revision pin and seal/warrant context, office chat and governing records, and command help/refusal are behavioural fixtures. WHY a heading cannot prove behavior and a scrub against empty tables proves nothing. Multi-upload scenarios are split at their durable steps within the existing per-case time budget, without raising a timeout. The complete sequence still runs, serially, once per named file.

Atomicity refinement: OLD upload proof did not plant a competing lock, isolate optional-database metadata costs or inject publication/journal failure. NEW a planted lock survives refusal; the final database plus manifests must fit before optional rows are admitted; prepared journal intent precedes rename and failure cannot leave a successful partial destination. WHY concurrency and crash boundaries need behavioral proof, without generating concurrent load.

Receipt/media refinement: OLD saved destination fields are unknown and missing report attachments always look stale. NEW bounded last receipt fields feed settings; an ordinary host job ingests one report, a retained C-class note and one secretary line idempotently; a restored omission index produces a declared omission for each file/image/video/audio renderer, while unexpected absence stays missing. WHY the offline uploader must keep evidence without requiring a server and restored reports must explain intentional exclusions.

Page criterion: OLD browser checks show only unknown upload receipts and generic attachment failures. NEW tests/storage-upload-pages.test.ts draws a populated synthetic last receipt/error and all four declared omission renderers, and photographs each changed page at 1440/990/660/390 in English/light/dark. WHY visible receipt and omission behavior needs an actual browser and inspection of every viewport/theme picture.

Ingestion identity criterion: OLD idempotence queried the record corpus by nested receipt JSON per report/notice/message. NEW the job uses a deterministic receipt identity with indexed primary-key lookups and complete report for/date fields; a query-shape guard refuses a receipt JSON corpus lookup. WHY a synchronous ordinary job must not scan the corpus hundreds of times to ingest bounded host receipts.

Bounded/concurrent/pin refinement: OLD only pre-read inventory mismatch and one overlapping historical pin were exercised. NEW tests/storage-folder-safety.test.ts forbids array directory listing and injects an unindexed file into an initially empty directory or a database write during copy; both must refuse publication. tests/storage-pinned-history.test.ts gives independent nested target/revision, parent record-object and sealed revision references plus a reader anchor, preserving each older pin while an older unpinned row is omitted. WHY no concurrent load is needed to prove these publication boundaries, and overlapping pin references can hide a broken reader.

Receipt identity and unsafe source criterion: OLD nothing said what happens when a receipt's record id is already taken, when a create throws inside the id turn, or when an upload fails; and a selected file or transcript holding a usable key or token hash had no rule. NEW tests/storage-receipt-identity.test.ts: a failed upload is filed as a complete report that says it failed and gives the uploader's reason; an id held by a record of another kind or attempt is refused, nothing is written and the receipt stays pending; a create that throws ends the id turn, and the next reading files the report. tests/storage-unsafe-source.test.ts: a selected file and a selected transcript that carry a key hash of the office are left out with the reason unsafe-source, in the pack's manifest and in the receipt's omissions; the safe file is kept; the restored copy treats the left-out file as a declared omission. WHY the deterministic id is safe only if a collision is refused and the turn cannot leak, a failed upload must not read as "0 bytes sent", and the canonical byte search decides what is unsafe while the uploader leaves such a file out by name instead of cleaning it.
