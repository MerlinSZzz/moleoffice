# Periodic original main suite receipts

1. Capture the clean main checkout's exact commit and tree without fetching, moving refs or changing its working tree. Run the captured commit in a separate clone through the cloud suite door. Never run a build or suite locally.
2. Ask the existing one-seat full-suite pool for its seat. A poll answering a firing that finds the seat taken keeps its place in the seat's line and waits inside that poll. It waits until the firing's time ends: the counter's next due time, or its held-back boundary when that is later. It asks again every 10 seconds with the same process row, as the merge queue does, and never gives back a place it still wants. When that time ends, or when it is asked to stop, it gives its place back. The poll's answer, skipped or pending, says that it waited and from when, its place in line when it last asked, and how long it may still wait. While it waits, the poll's journal step is `in line`. The step `running` is written only when the seat is granted, so a poll that ended in line is not taken for an interrupted suite. Started by hand without a counter, the producer gives a queued place back at once and says which place it had. The receipt's start time is when the seat was granted. Issue no unbounded queue-list read. Hold the seat until the bounded door and cleanup have finished, then release it on every outcome. The door shares the recorded producer group, so its continued life also keeps the slot held if the producer leader exits.
3. A busy or unavailable box returns not run with its actual reason. File no receipt from that result and never fall back locally. Periodic checks are at least a minute apart. A firing of the counter runs the suite at once, and the counter alone spaces the runs, never closer than its 30 minutes; unchanged main with an existing receipt is skipped. Started by hand without a counter, the producer starts actual runs at most once every two to three hours.
4. File one whole_suite_receipt from the original cloud build and suite results, before any attribution or rerun. Keep the full commit/tree, location, local timestamps, actual exit codes, all failing file/test names, complete manifest coverage result and hashed artifacts. Successful build is a prerequisite for suite facts. A failed build leaves suite facts absent.
5. Derive green in one shared contract. It requires build and suite exit zero, no failing tests/files, positive complete expected/observed coverage, and log/report/manifest/read-record artifacts. Compare the original report with the expected manifest; no subset, borrowed result or queue green verdict is a substitute. Preserve full manifests in the hashed artifacts and compact coverage counts/differences in the receipt.
6. Validate commit identity, result/exit agreement, original reporter counts, safe paths and artifact contents before filing. Unknown, cut or contradictory evidence fails visibly. An unfinished attempt remains recorded with its recovery directory; do not quietly rerun a suite after an unknown write.
7. Changing another record into whole_suite_receipt is refused with 409 and writes nothing. A receipt may change out of its kind while retaining its facts. The generic kind-change sweep covers those allowed directions.
8. Tests use throwaway main repositories, a throwaway office and explicitly labelled synthetic cloud artifacts. Every new test has a green control, a specific mutation that turns it red, and a green restore. No test reaches the live office or cloud box. The periodic runner is built here; activating it and switching the office are later operations.
9. An exit-zero answer requires the original report's successful summary and zero failing suites. The suite totals and every passed, failed, pending and todo assertion count must agree with the actual rows. A nonzero whole run with Vitest's unhandled "Worker exited unexpectedly" error may explain a positive test-count gap only when it equals exactly the pending assertions in named files; passed, failed, skipped and todo counts must still agree. The receipt names each affected file and how many tests never finished in workerCrashes, without calling those tests failed assertions. Each affected file is red and runs alone under the existing version-2 rules. The unhandled error count stays unchanged, so it still prevents green even when the files pass alone. Every other disagreement is refused. An older office whose receipt kind has no workerCrashes field gets the crash names and counts in the receipt's summary, also named in the producer's answer; its hashed original report and log keep the evidence. Rebuilding such an older receipt checks the same count explanation and does not invent the later field.
10. A not-run answer that includes actual build or suite phase evidence preserves the consumed cadence and unfinished recovery state. It does not mean the box was busy before starting. A stop request waits for an already-started door's bounded result and cleanup before giving back the seat.
11. The registered door's host process group must match the granted seat's host holder group before the gate opens. A wrongly named caller resource fails before cloud work starts. The office's readings supply both identities, including when the caller is inside a container.
12. SIGTERM or SIGINT sent to the recorded producer group requests graceful completion. The door gate handles those signals too, because it shares the group. It keeps the door alive until its bounded call and cleanup finish. Force-killing the whole group is an interrupted, unverified attempt, and must not be described as successful cleanup.
13. A phase-less not-run reply does not prove that work never started. The exact busy refusal or commit-transfer refusal, without phase or exit evidence, clears an attempt without consuming its cadence. Both are issued before the cloud build or tests start. A timeout, lost reply or other unknown outcome keeps its recovery marker and reserves the attempted start time. No build or suite exit is invented. The genuine busy retry remains allowed.
14. A file is red by the one rule in tools/a-passed-test-file.mjs, which the merge tool's red-files.mjs also reads: it passed only when its own status is passed and every test in it ended passed, skipped or todo. So a file vitest calls passed, with a test that never ran, is a failed file of the receipt.
15. The producer asks the door for runs alone with `--alone <attempt>/alone`. When the whole run was red and the door ran each red file alone, the producer files version 2 of the receipt. Its aloneRuns names every failed file once, in the same order, with what its run alone gave: green, red, no result (with the reason) or not run (with the door's reason). The reasons for no result are the merge tool's, in its order: no readable report, a report that does not name the file, a command stopped before its end (124, 137 or 143). A run alone is green only when it exited 0 and its report names the file and every file in it passed. The whole run's facts are filed unchanged, and errorsOutsideTests counts the errors vitest's summary reports outside the tests, absent when the summary cannot be read. Runs alone that do not match the red files are refused, and nothing is filed.
16. An office that does not take version 2, because its kind has neither of the two new fields, gets version 1 with the same whole-run facts, and the producer's answer says so and names what each red file did alone. An office with one of the two fields only is refused. A red whole run for which the door returned no runs alone is filed as version 1, and the answer says the door returned none. The producer's answer always lists the files green, red, with no result and not run alone.
17. The schedule is the counter that requests the job: it follows landings on the main checkout and has two triggers, a count of MOLE_OFFICE_MAIN_SUITE_LANDINGS landings (6 when unset, a whole number from 1 to 100) and every MOLE_OFFICE_MAIN_SUITE_HOURS hours (2 when unset, above 0 and at most 24). Its 2-hour trigger waits for at least one landing, so the suite runs only when main has moved. A value outside those limits is refused, naming the setting. `run-the-main-suite-job.mjs --file-the-counter --repository <main>` files that counter once, under the runner's own agent, and says the setting line that turns it on; it refuses when MOLE_OFFICE_MAIN_SUITE_COUNTER is already set.
18. Each poll compares the counter's triggers with the two settings, by kind and number only. When they differ it puts the settings' triggers back with one change that names both settings as the reason, and goes on from the counter the change returned. A counter that still reads other triggers after that change is refused, and its firing stays unanswered.
19. Started by a host timer with no process row named, the runner registers its own process for the seat just before the producer starts, and requires the office to read its process group as the runner's own, which it is only when started under `setsid -w`. Otherwise it lets the row go and stops before the producer, and the firing stays unanswered. The row is let go, without a signal, at the end of every poll that registered it.

20. Trace failedFiles from a verified red receipt, tracing every version 1 failed file and only version 2 files red alone, and say why each other file was not traced.
21. Use only the previous receipt answered by this counter as the baseline when that file did not fail there; otherwise say no earlier receipt or red since at least that receipt.
22. Read at most 200 commits of ordered merged landings with one narrow entry read, report their uncovered gaps, and halve over their main boundaries while retaining visited and unvisited boundaries.
23. Run both mainAfter with the landing and mainBefore without it again and hand back only when the first is red and the second green.
24. A gap, unavailable result, observed nonmonotone answer, unreadable evidence or exhausted run budget is unknown and names no responsible landing.
25. Trace at most five files and run each alone at most eight times including both confirmations, saying which limit stopped any remaining trace.
26. The original receipt filer proved by its own agent key hands grouped files back once per landing through a door that checks merged state, both commits and exits, original repository and main ancestry, failedFiles, version 2 reds alone and the open round before writing the landing path's exact problem and notices, or naming an existing open problem and unnamed files through a narrow read.
27. A verified red receipt enters journal step tracing before answering, keeps its result and per-file boundary evidence in the journal and the bounded firing answer, retries an interrupted tracing step safely, and a green receipt never traces.
28. A poll reads its firing's moment from the instant the office publishes beside the row's stamp, `atInstant`. On the night the clocks go back a stamp can name two moments an hour apart. An office that publishes no instant, and a row with a null instant because it was written before the office kept one, are read from the stamp in the poll's own zone. Where the stamp names two moments, the later is taken, so a poll that could come before its firing is refused and never let in. An instant that names no moment, and a stamp that names none, are refused. The poll's result says which it read in `firingMoment`, and the command prints that line before its JSON.
29. Before the door, the producer reads the receipt its state names as the last one, from that receipt's original create revision, and takes the files its runs alone left not run. It passes them to the door with `--carried-over`, so after a red whole run those that are red again run alone first (the door's criterion 26). With no last receipt, a version 1 receipt, or none left not run, it passes nothing and the order is the door's sorted order. A last receipt that cannot be read is said, with the reason, in the answer and in the receipt's summary, and the run goes on passing nothing; nothing is guessed. The office's receipt kind has no field for it, so the receipt's summary names the carried-over files that ran alone first, and those not red this time; the attempt keeps `carried-over.json` with the list passed and where it came from; the answer gives `carried`. A door answer whose `carriedOverFirst` is not the red files of that list, in its order, is refused and nothing is filed. The runs alone are filed in failedFiles order, as before.
30. A door answer that the whole run hung (the door's criterion 27) ends the attempt. The producer keeps the hung records in `<attempt>/hung.json`, files no receipt, and clears the pending attempt, because its cause is recorded, so the next firing runs. The firing fails, and its failure names each hung file and its wait and the records' path. A report the suite wrote while tests were still running is never filed as counts.
31. Every office call the producer makes, and every call of the poll that runs it, waits at most 120 seconds for its answer, the one bound `PRODUCER_OFFICE_ANSWER_WAIT_MS` in tools/periodic-main-suite.mjs. That covers the seat's asks and the poll's reads, answers and releases. A call still unanswered then ends as one the office did not answer, with the reason its fetch gave, as before. Why: the live office's run-finishing writes hold its request thread, for 12.5 seconds on average and up to 278 seconds, and a call waits behind them. At the earlier bound of 15 seconds, firing 1012 failed at its first call and ran no suite.

Criterion correction before implementation: the old rule treated every exit-75 not-run reply without phase fields as unstarted. The new rule permits that only for established pre-run refusals. The door can time out after entering the suite and return no phase fields; their absence cannot justify another suite a minute later. Audit Cwad6lciToAw found that concrete path. The existing real-door controls exercise a failed commit push before the remote run command; that exact refusal also proves the suite never started. Their expectations stay unchanged.

The existing kind criteria change with the new kind: the attachment and normal-mode lists gain whole_suite_receipt; the developer panel's incomplete fixtures change from 32 to 34 because the new kind has two fixture modes; the seed list gains an explicitly unseeded kind because no demo is an observed suite. The kind-change sweep previously had no receipt-specific exclusion; it now excludes another kind becoming a receipt, while keeping the other tested directions. The generic panel fixture title changes from "Fixture whole_suite_receipt record" to "Made-up incomplete receipt — no cloud run" so its provenance is more explicit. Existing cloud-door expectations stay intact; optional manifest cases add expectations for original phase/exits, contained paths, masks and cleanup.

The Reports and notes family criterion formerly named 21 kinds. It now names 22, adding whole_suite_receipt after merge_entry: a receipt is an account of an observed run, not work to do. The all-refusal probe still requires every declared code; its new receipt case exercises the real 409 in Chinese mode and keeps the error in English. No count or expectation is weakened. The declared cloud-box option needs an English option word so the normal editor names it and the translation waiting list can account for it; no Chinese is added.
