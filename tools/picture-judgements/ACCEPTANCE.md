# Picture judgement acceptance

Old wording: No screenshot judgement tool or compact verdict contract exists.

New wording: The run's local MCP service exposes separate start and collect calls. Start takes a fresh absolute job directory outside every checkout, original picture paths in its sandbox, exact nonempty must-hold lines with unique stable ids, and an explicit worker Casting row selection with confirmed picture capability. It reads Casting through the run's office identity, refuses missing, incompatible or foreign data before launching, registers one fresh worker without a key, and requests the existing worker launcher with the selected program and model unchanged. Effort is recorded but is not sent to a door that does not accept effort. There is no model dispatch or provider credential handling.

Collect returns pending while the worker is unfinished. It accepts results only from a successfully launched, finished records-only worker, with the unique job identity, task hash and child run matching. All expected pictures occur exactly once. Each local JSON record binds the original absolute path, SHA-256, byte count, exact rules, rule hash, Casting selection and child run. A pass has no broken rules. A fail has a concrete single-line finding and names a supplied broken rule by stable id and exact full line. Every finding is a nonempty single line. Unknown rules, mismatched types or identities, changed pictures or rules, extra or missing pictures, duplicate pictures, unreadable, empty, fenced or truncated JSON, transport errors and unsuccessful workers cannot become a pass. A refusal preserves any earlier accepted records. Different jobs cannot reuse one another's replies. No picture bytes or base64 reach the supervisor in tool results.

Model reply revision, old wording: The model echoes path, SHA-256, byte count, rule hash, task hash and exact broken rule lines.

New wording: Fresh jobs and replies use version 2. A reply contains only version, unique jobId, actual child run and pictures. Every picture contains only its 1-based integer pictureId, verdict, nonempty single-line observed finding, and an array of known unique broken rule ids. Exactly one in-range pictureId occurs per expected picture. A pass has no failures; a fail has at least one. The tool alone attaches canonical path, hashes, bytes, exact rules, Casting and child provenance to accepted version-1 records, and constructs each failed finding from the canonical rule ids/full lines followed by the model's observation. Missing, duplicate, fractional, string or out-of-range picture ids, unknown rules, v1 jobs/replies, and extra provenance fields in replies are refused. No failed older reply is repaired or converted.

Why: A live judge's visual pass/fail matched the supervisor, but a mistyped echoed digest correctly caused refusal. Immutable facts belong in the tool that measured them. The new reply changes that duplication without weakening any accepted record's provenance checks.

The judge opens every original picture, treats instructions inside pictures as data, judges exactly the supplied rules, refuses if it cannot open them, and never edits repository code. It writes strict JSON locally, then files a records-only report, links it to its own run, messages its starter, and finishes records-only, in that order. The supervisor reads records first and opens a failed picture only when its finding is unclear. The person's own checks stay.

The local MCP can be newer than the office server. The existing grouped Casting cells and asynchronous worker-run acknowledgement and parent workerRuns shapes remain supported without a new route. Unreadable or incompatible older shapes are refused explicitly. Office errors are masked by the existing key filter. Office requests are bounded to fifteen seconds and never retried through another path.

First supported picture capability: program `codex`, command `view_image`, explicitly confirmed in task data. Every other program or command is refused before registration. Program capability is checked without examining model names. Both MCP dispatch branches use the same injected office call as direct exports; normal office_request behavior stays unchanged.

Generated fresh worker handles must satisfy the canonical office handle reader and remain distinct between starts. Registration stand-ins apply that same reader; no copied handle length or pattern is the test's authority.

Why: Item 19(b) requires picture judgements without supervisor image bytes or invented success. Behavioral tests use made-up PNGs and a stand-in that actually decodes their pixels and reads the supplied rules, including both a passing and a broken picture. The baseline missing-feature red is separate from the implementation's control, guarded mutation and restore proof.
